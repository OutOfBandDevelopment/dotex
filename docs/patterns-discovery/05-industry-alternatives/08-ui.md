## 23. UI architecture and JS/TS framework choice

**Today:** no UI projects exist in the solution. The stated preference is MVVM with command binding wherever possible (WPF), and for required JS/TS frameworks the closest available equivalent ([UI practices](../03-practices-and-conventions/08-ui-practices.md)).

**Table 24 — UI architecture options**

| Option | Pros | Cons |
|--------|------|------|
| MVVM with command binding (WPF; CommunityToolkit.Mvvm helps) | Logic testable without a UI; declarative bindings; matches interface-injection style | Binding errors surface at run time; boilerplate without a toolkit |
| MVVM with lambda-routed commands (`RelayCommand(() => ...)`) | Least code | Logic is anonymous and only testable through the view model; not the preferred form (commands should be real, retestable types) |
| MVC or MVP | Familiar; explicit controller | More glue code; view logic leaks into controllers |
| MVU / Elm-style unidirectional flow (Redux, Fabulous, Blazor patterns) | Predictable state, easy time-travel debugging | Different mental model; more ceremony for simple forms |
| Code-behind | Fastest for small tools | Untestable; logic tied to controls |

**Table 25 — JS/TS frameworks by fit to MVVM (general knowledge; re-check before deciding)**

| Framework | Fit | Notes |
|-----------|-----|-------|
| Knockout | Closest | Observables, computed values and declarative bindings are essentially MVVM; older and less active |
| Aurelia | Very close | Convention-based view/view-model pairs with two-way binding; smaller community |
| Vue | Close | Reactive state with `v-model` and event handlers; composables or Pinia stores act as view models; commands are convention, not a type |
| Angular | Moderate | Components with two-way binding and services; RxJS and signals instead of `ICommand`; strong DI matches the framework's style |
| Blazor | Close for .NET teams | C# view models with binding; MVVM needs a toolkit and discipline because components mix view and code |
| React | Furthest | One-way data flow and hooks; view models are custom hooks or stores, no built-in binding or commands |

**Verdict: Keep the preference.** Default to MVVM with commands for desktop UI. For web UI prefer Vue or Angular for a mainstream choice and Knockout or Aurelia for the closest model, and where React is required, structure view models as hooks or stores that own state and expose command-like functions so the same testable seam exists. Record the choice as an ADR when a UI project starts.

**Owner decision:** spikes wanted for Blazor, Knockout and Vue, a survey of component-library options for UI controls, and a WPF proof of concept because not everything is web.
