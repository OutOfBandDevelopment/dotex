# Aeotec Z-Stick S2 on COM13: first contact and the `zwave` plugin

First real-hardware pass for the Z-Wave plugin (`src/DevTerm.Devices.ZWave`, branch `dev/zstick-s2`, built on `9ff1cd7` plus uncommitted work). Read-only: no paired node was switched.

## Device configuration matrix

| Device | Role | Profile | Transport | Framing | Result |
| --- | --- | --- | --- | --- | --- |
| Aeotec Z-Stick S2 (Z-Wave 2.78, home ID `016A1C28`) | USB Z-Wave controller, node 1, SUC | `zwave` presenter (plugin) | Serial, COM13 | 115200 8N1, DTR/RTS on, no terminator | Confirmed working |

## Commands tested and responses

Run with `dotnet run --no-build --project src/DevTerm.Console -- --transport serial --port COM13 --baud 115200 --presenter zwave --parser zwave --cli true`, one line typed per row (bare function id, or `function payload`; the parser prefixes an ACK).

| Sent | Received (presenter output) |
| --- | --- |
| `15` | `RES GetVersion: Z-Wave 2.78, static controller` |
| `20` | `RES MemoryGetId: home ID 016A1C28, this controller is node 1` |
| `02` | `RES SerialApiGetInitData: 26 nodes (1-12,14-21,23-24,27-30), API version 5, chip 3 v1` |
| `41 02` | `RES GetNodeProtocolInfo: listening, routing, Routing Slave, Binary Switch (specific 0x01)` |
| `56` | `RES GetSucNodeId: SUC is node 1` |
| `13 02 02 20 02 25 07` (Basic Get to node 2) | `RES SendData: accepted for transmission`, then `REQ SendData: transmit #7 no acknowledgement from the node` |
| `41 03`, `41 63` | `GetNodeProtocolInfo` for nodes 3 (sleeping Remote Controller) and 99 |

Raw frames captured from the first pass (also the fixtures in `ZWaveDecoderTests`): `06 01 10 01 15 5A 2D 57 61 76 65 20 32 2E 37 38 00 01 9B` (version), `06 01 08 01 20 01 6A 1C 28 01 88` (memory id), `06 01 04 01 05 18 E7` (controller capabilities), `06 01 04 01 56 01 AD` (SUC), and the 0x07 capabilities frame (manufacturer `0x0086` Aeotec, product `0x0002/0x0001`).

The opt-in test `RealHardwareZStickTests.Refresh_AgainstRealStick_ReportsLibraryAndHomeId` (`dotnet test tests/DevTerm.Devices.ZWave.Tests --settings devterm.runsettings`) drives the panel's `ZWaveControlSurface` (Refresh, then Node info for node 1) and passed: version, home ID, capabilities, init data, SUC and `GetNodeProtocolInfo: listening, Static Controller` all answered, no CAN.

## Findings

- **The host must ACK every data frame.** The stick answers a request with `06` (its ACK of ours) and then the data frame; a frame we never ACK is retransmitted and the next request is answered with `CAN`. Typed lines carry a leading `06` for this, which was harmless on the stick.
- **Unsolicited callbacks need an ACK too.** A `SendData` to a node that does not answer produces repeated `REQ SendData` callbacks (`transmit #7 no acknowledgement`), then `CAN` on the next request, and in the CLI the serial transport reported `Connection lost: timed out - no response to hardware flow control (CTS)?` and reconnected on the next line. The CLI has no ACK-on-receive, so this is expected there. The panel's `ZWaveAckResponder` ACKs each data frame as it arrives (verified by the passing test above for the Refresh and node-info path; a Basic Get through the panel to an unreachable node was not exercised).
- Nodes 2 to 7 did not acknowledge a Basic Get (battery nodes asleep, or out of range); this pass did not try to switch anything.
- Node 1 is both the controller and the SUC; 26 of 30 possible nodes are included.
