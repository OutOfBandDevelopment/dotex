## Goals

1. Search one document set through two independent providers, lexical (inverted index, OpenSearch) and semantic (nearest neighbour over embeddings, Qdrant), and return one ranked list.
2. Keep every provider replaceable: callers depend on `IVectorStore<T>` and the factories, never on Qdrant or OpenSearch types.
3. Select a vector collection by type or name with no registry of concrete providers.

## Non-goals

- Re-ranking from user behaviour (the neural re-ranker in the overview is an idea, not planned work).
- Document storage, conversion, packaging and authorization; they have their own designs ([document packaging request](../../features/request/2026-11-10-document-packaging-and-store.md), claims in the identity design).
- Choosing an embedding model; the embedders live in `OoBDev.Onnx.*` and `OoBDev.Ollama`.

## Requirements

<a id="table-1"></a>**Table 1 — Requirements and state**

| Id | Requirement | State |
|----|-------------|-------|
| R1 | A vector store stores embeddings with metadata and returns ids (`IVectorStore.StoreVectorsAsync`) | Built (`OoBDev.Search`, Qdrant adapter) |
| R2 | A vector store lists items and finds nearest neighbours, optionally grouped by a metadata key | Built (`ListAsync`, `FindNeighborsAsync`) |
| R3 | The collection comes from `[VectorStore]`, then `[Table]`, then the type name | Built (`VectorStoreFactory.Create<T>`) |
| R4 | A provider is chosen by keyed service, then by the provider factories, then by the default provider | Built (`VectorStoreFactory.Create`) |
| R5 | A lexical provider queries OpenSearch and indexes a document | Not built: only options and the client factory exist |
| R6 | A hybrid query runs lexical and semantic in parallel, joins by path hash, rescales lexical scores by the maximum and keeps the larger of the two scores per item | Not built: the algorithm is recorded in [api-design](api-design.md#planned-hybrid-contract); the obsolete `HybridProvider` shell was removed 2026-11-11 |
| R7 | Results carry a score, an item id and metadata, and report which search type found them | Partly built: `SearchResultModel` has score, id and metadata; the type flags (`SearchTypes`) are not on the model |
| R8 | A document summary is generated by chunking the text and summarising the chunk summaries | Dropped: the `DocumentSummaryGenerationProvider` shell was removed 2026-11-11 (chunk, summarise each chunk, summarise the summaries; rebuild over `IChatClient` if needed) |
| R9 | Search types are a flag set (`Semantic`, `Lexical`, `Hybrid`) | Built (`SearchTypes`; `None` is 0) |
| R10 | Every behaviour above has a test in `OoBDev.Search.Tests` | Not met: the project has no tests (see [testing strategy](testing-strategy.md)) |

## Constraints

- Framework layer: `OoBDev.Search` depends on `OoBDev.Search.Abstractions` and `OoBDev.AI` only; adapters reference the abstractions (rule `coding-standards`).
- Services outside the process run in Docker for tests (Qdrant, OpenSearch are in the integration stack).
- Hashing defaults to SHA-512 where a path hash is computed (owner preference); the commented code uses an existing `PathHash`.

## Open questions

- Is the hybrid merge (R6) rebuilt as a first-class `IHybridSearch` in `OoBDev.Search`, or does the example application keep it? Recorded as a backlog line; build only when a consumer needs it, like the other design-first features.
- Decided (autonomous default, 2026-11-11, reversible through git): the three obsolete provider shells were removed outright; the merge algorithm stays in [api-design](api-design.md#planned-hybrid-contract).
