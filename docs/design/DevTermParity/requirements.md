## Problem statement

dev-term (`C:\repo\oobdev\dev-term`) is a device terminal: it opens a connection to an instrument or gadget, decodes the bytes, shows them and lets the user send commands. The owner requires the OoBDev version to have 100% parity with it: every protocol and every feature, with feature parity but not interface parity (the contracts follow this repository's patterns, see the [restructure plan](restructure-plan.md)).

## Goals and non-goals

Goals:

- Every dev-term feature exists in `OoBDev.DevTerm.Core` and in the three front ends (`Wpf`, `Tui`, `Web`), with its tests.
- Transports are reusable `OoBDev.System.IO.*` libraries, independent of the decoders and zero-copy.
- Device panels, settings and decoders live with their protocol libraries and are described with the generic `UiDefinition`.

Non-goals:

- Interface parity with dev-term (`ITransport` is replaced by the pipe-based `IDeviceAdapter`).
- A dependency from Framework or the device libraries on `src/Applications`, and a dependency from DevTerm Core on any device library.
- Porting dev-term's own test helpers or its coding-standards test (this repository's rules and `OoBDev.Devices.TestUtilities` apply).
- Porting dev-term bug reports; open bugs become backlog items when their code is ported.

## Requirements

Priority: **M** Must, **S** Should, **C** Could.

**Table 1 — Engine requirements**

| Id | Requirement | Priority |
|----|-------------|----------|
| REQ-001 | A `Session` binds one `IDeviceAdapter` to a `Pipeline` of decoders and presenters and exposes the decoded output to observers. | M |
| REQ-002 | A message router sends decoded messages to consumers by rule, including loopback routing between sessions. | M |
| REQ-003 | Text presenters (ASCII, UTF-8, hex, decimal, octal, binary, key/value) are available by name through a presenter catalog. | M |
| REQ-004 | Device manifests (JSON and XML, `.ksy` import) describe a device and produce a generic panel without code. | M |
| REQ-005 | Connections are stored as configuration with typed editors; device-specific settings are edited through `IDeviceConfigEditor` supplied by the device library. | M |
| REQ-006 | Session logging records traffic and supports playback. | M |
| REQ-007 | Plugins load from assemblies at runtime, with a trust check before anything is loaded. | M |
| REQ-008 | Schemas for the configuration and manifest files are generated, with ids `oobdev://devterm/schemas/<file>`. | S |
| REQ-009 | Telemetry uses the host-free `OoBDev.Telemetry` exporter. | S |

**Table 2 — Transport and device requirements**

| Id | Requirement | Priority |
|----|-------------|----------|
| REQ-010 | Serial, HID, TCP (with LXI discovery and XON/XOFF), RFC 2217 and VXI-11 are `OoBDev.System.IO.*` adapters over the pipe contract. | M |
| REQ-011 | USBTMC, BLE, MQTT, AMQP and STOMP transports exist with the same contract. | M |
| REQ-012 | A loopback adapter lets every front end and test run without hardware. | M |
| REQ-013 | Each of the eight device libraries (Busylight, DE-5000, K8055, NMEA, Radex One, SCPI, Z-Wave, Zoom H4n) provides its control surface, `UiDefinition` and decoder in a `.Panels` sub-namespace. | M |
| REQ-014 | A demo device is available for the shells. | C |
| REQ-015 | Core registers panels through `AddDevTermDevicePanels()` and resolves them through DI. | M |

**Table 3 — Front end requirements**

| Id | Requirement | Priority |
|----|-------------|----------|
| REQ-020 | `OoBDev.DevTerm.Tui` provides the CLI and the full-screen text UI with every dev-term screen (main window, editors, stream monitor, routing, playback, control panels). | M |
| REQ-021 | `OoBDev.DevTerm.Web` serves the same screens, a panel API, a session hub and an AsyncAPI document. | M |
| REQ-022 | `OoBDev.DevTerm.Wpf` provides the desktop shell with the same screens and renders `UiDefinition` panels. | M |
| REQ-023 | The user guide has the dev-term task guides with current screenshots, generated by tests into `artifacts`. | S |

**Table 4 — Quality requirements**

| Id | Requirement | Priority |
|----|-------------|----------|
| REQ-030 | Every requirement above is covered by a test row in the [testing strategy](testing-strategy.md); hardware, broker and browser tests are `DevLocal` or `Hardware` and end `Assert.Inconclusive` when absent. | M |
| REQ-031 | Framework transport libraries reach 80% line coverage; DevTerm Core targets 85%. | M |
| REQ-032 | One top-level type per file, nullable on, XML docs on public APIs. | M |
| REQ-033 | Nothing in `System.IO.*` references DevTerm; Core does not reference device libraries. | M |
