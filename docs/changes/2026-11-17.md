## Keycloak realm roles grant application rights (403 for grace in the example)

- Cause: Keycloak puts realm roles in the nested `realm_access.roles` claim, but `RoleRightClaimsTransformation` only read flat claims (`role`, `roles`, the .NET role type) and the example realm has no mapper that flattens them, so every signed-in user, `grace` included, got no application rights and every `[ApplicationRight]` endpoint answered 403.
- Fix: new option `RoleObjectClaimTypes` (default `realm_access`); the transformation reads the `roles` array of those JSON claims (malformed JSON grants nothing). Documented in `CONFIGURATION_SETTINGS.md`, the ApplicationRights design and `dev-users.md`.
- Tests: 2 new Unit tests in `RoleRightTests` (12 pass). Not run against a live Keycloak: sign in as `grace` again after rebuilding the API to confirm. Only the `admin` role maps to rights in the example, so `ada`, `alan` and `margaret` still get 403 on the guarded endpoints.

## Integration tests start and wait for their containers

- `[IntegrationTestMethod("oobd-test-x")]` (`OoBDev.TestUtilities.Containers`) now marks the Integration tests of 30 projects. Before a test it checks the containers, starts the ones that are down (`docker start` or `docker compose up` of one service) and waits for the health check; after `CONTAINER_STARTUP_TIMEOUT_SECONDS` (default 5), or without Docker, the test ends Inconclusive. Only containers the tests started are stopped, and only by the last test process still using them (lease files shared between processes, so parallel test projects never stop a container another one is using).
- Every health check in `docker-compose.integration-tests.yml` gets `start_interval: 1s`, so containers turn healthy in seconds, not after the 10 s interval.
- Parameters `CONTAINER_STARTUP_TIMEOUT_SECONDS`, `CONTAINER_AUTOSTART`, `CONTAINER_STOP_AFTER_TESTS` in `src/.runsettings` and `TEST_VARIABLES.md`; 11 Unit tests with a fake Docker; verified with the Redis Integration tests (container stopped: started, 6 passed, stopped; autostart off: skipped as Inconclusive; two runs at once: stopped only after the second finished). The other 29 projects build; their Integration tests were not run.

## GitVersion patch jump explained

- The jump from `0.5.74` to `0.5.1056` is the Mainline policy: the patch counts every commit that reaches `main`. Since `v0.5.0` there are 75 first-parent commits (the merges, about 74) but 1316 commits in total, so merging a branch of about 980 commits adds them all at once. No fault; recorded in `GitVersion.yml`. Tag a new base (for example `v0.6.0`) to reset the patch if the large number is unwanted.
