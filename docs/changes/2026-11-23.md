## Desired-state bake-off: Atlas on PostgreSQL

Ran Atlas v1.4.2 (vendor binary downloaded to a scratch folder, owner approval Q29) against the test PostgreSQL container with throwaway databases. Plain tables and indexes pass, but views and extensions need an Atlas account login, renames plan a drop and add, drops and drift are planned without a gate, and the data-loss diagnostics are login-gated. That breaks REQ-008, so Atlas is out; sqldef and pgschema remain. Recorded in [the bake-off result](../design/DesiredStateDatabase/bake-off-result.md#atlas-on-postgresql). Not run: Atlas on SQLite and SQL Server.

## Example web: live check of the Schedule and Address lookup pages

Drove both pages in a real browser (Playwright, a bearer token for the Keycloak test user added to the API calls) against the real example API and the Vite dev server. Address lookup returned the matched White House address with coordinates and quality from the public Census service; Schedule moved an item due in 3 s from pending to fired. A first attempt also showed a damaged `obj` tree left by an interrupted build (75 NUL-filled generated files), removed and rebuilt clean.

## Example Data access: live pass with a real read-only login

Ran the example API against a throwaway SQL Server database with a `db_datareader` login (created and dropped afterwards) and a Keycloak token for the `data.query` right. A SELECT returned its rows; `DELETE` and a two-statement text were refused with 400 problem details; a query on a missing table gave 502; a query on `sys.sql_logins` showed the login names but `password_hash` came back null, because the login has no server permission; no token gave 401. The database-level read-only protection itself was not exercised, since the parser refuses writes first.

Not run: a live pass against the real API.
