## Playback checkpoints

- `SessionLogger` writes a marker-only `checkpoint` record after every 500 received chunks (`checkpointEvery`; 0 turns it off). Older readers keep it as an unknown record and playback text skips it.
- New optional `ISnapshotPresenter` (`Snapshot()`, `Restore(object?)`), implemented by the ASCII, key-value, hex, binary, decimal and octal presenters; `Pipeline.TakeSnapshot` and `RestoreSnapshot`. `Utf8Presenter` followed later the same day (see below).
- `PlaybackEngine` takes the snapshot when it plays a checkpoint and, on a backward seek, restores the nearest earlier one and replays only the records after it. Per-record outputs are cached so the reset batch still holds the whole transcript; `AddNote` and `ChangePipeline` drop stale cache entries.
- Design: `docs/design/SessionLogging/session-logging.md`. Tests: 9 new Unit tests (`PlaybackCheckpointTests`) plus the existing logging tests pass (53 in the filtered run).

## DevTerm TCP services

- `ServiceHostBridge` (DevTerm.Core, an `IDeviceAdapter`) hosts the echo, discard, daytime, time or chargen server so a session shows what clients send; the server's replies surface on `Replied`, and anything typed in the session is dropped because the service decides its replies. It binds loopback by default, and a port that cannot be bound throws an `IOException` naming the address.
- `ServerBase` gained a `Traffic` tap (bytes plus direction; a throwing observer is ignored) and a protected `SendAsync` that the echo, daytime, time and chargen servers now use. `DisposeAsync` no longer rethrows the cancellation and socket errors that stopping causes. `ChargenServer` takes `maxBytesPerClient` (default 64 KiB, 0 for no limit).
- CLI: `--transport service --service <echo|discard|daytime|time|chargen> [--port N] [--host ip]`, validated, described and added to the connection editor and the profile schema.
- Design: `docs/design/DevTermParity/generic-services-plan.md`. Tests: 8 `ServiceHostBridgeTests` plus validator tests (Core Unit run: 1101 passed, 5 skipped).

## Applesoft BASIC parser and tokenizer

- `ApplesoftParser` reads a listing into `ApplesoftLine` > `ApplesoftStatement` > `ApplesoftElement` (keyword with token code, or literal text). It works at the interpreter's lexical level: spaces outside strings are ignored, the longest keyword wins (`SCORE` is `SC OR E`), `REM` and `DATA` bodies stay literal. Bounds: 239 characters per line, line numbers to 63999, 1 MiB per listing; bad input throws `FormatException`. No expression tree is built (the request's AST is the statement and element structure; a grammar-level tree is not built).
- `ApplesoftTokenizer.Tokenize` writes the binary form `Detokenizer` reads (length, next-line addresses from 0x0801, zero terminators). `TokenMap.Keywords` exposes the keyword table; the table uses non-breaking spaces, which the parser also treats as whitespace. The Detokenizer adds a space after `REM` and `DATA`, so a detokenized listing re-tokenizes byte for byte only for lines without them.
- 6 Unit tests passed (token bytes, keyword-in-name, REM/DATA, bad input, detokenize read-back, byte round trip).

## DOS 3.3 disk image write support

- `DiskImageWriter` (`IDiskImageWriter`) adds, replaces and deletes files in a DOS 3.3 image: catalog slot (a never-used or deleted entry), chained track/sector lists of 122 pairs with sector offsets, data sectors zero-padded, bitmap bits and last-allocated track in the VTOC, file size in the entry. Names are 1 to 30 printable ASCII characters without a comma, stored upper-case with the high bit. The image is loaded to memory (geometry and size validated, 4 MiB cap, catalog and list chains loop-guarded) and written back in one piece only on success.
- 10 Unit tests passed on the sample image (read back through the reader, bitmap counts, a 130-sector two-list file, replace, full disk leaves the bytes identical, delete frees and marks, bad names, non-DOS streams). Real-disk behaviour in an emulator was not checked.
- Reader rough edges that stop files over 122 sectors being read back are in the backlog (DOS 3.3 reader rough edges).

## EcoWitt local TCP API decoder

- `EcoWittLocalApi` builds the five-byte request and checks the response framing (`FF FF`, command, size, data, checksum as sum modulo 256; the live data command uses a two-byte size). `EcoWittLiveDataDecoder` turns the live data response (command 0x27) into an `EcoWittLiveReading` in the metric units the gateway sends (temperatures, humidity, pressure, wind, rain periods, light, UV). An unknown or truncated field is reported in `Problems` while the values before it are kept; bad framing throws `InvalidDataException`. It does no I/O, so no cloud credentials are involved.
- 6 Unit tests passed (request bytes, full packet, unknown field, truncated field, bad framing, other command). The field table is from the published protocol description, not a device capture; ids after 0x17 (extra sensors, batteries) are unknown, so decoding stops at the first one and reports it.
