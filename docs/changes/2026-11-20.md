## Sandbox: message rate limiter

`MessageRateLimiter` counts frames per one-second window, drops the excess and counts it, and reports a sustained excess (default three windows in a row). `BrokeredPlugin.RateLimiter` applies it in the call loop: excess frames are skipped, a sustained excess throws `InvalidOperationException`. Three Unit tests with `FakeTimeProvider` pass. Not done: reading the limit from a manifest `msgPerSec` field, and heartbeat enforcement.

## Sandbox: heartbeat check

`PluginHeartbeat.Check(plugin, timeout)` sends a heartbeat frame and waits for the frame that acknowledges it; on a miss it disposes the plugin and returns false. `PlainPlugin.Dispose` is now safe to call twice. Two Unit tests pass (echo answers; a sleeping plugin is declared hung and stopped). Not done: running the check on a schedule and the restart policy.

## Sandbox: manifest message rate limit

The manifest takes an optional `Limits` (`PluginLimits.MsgPerSec`). `PluginHost` gives every started plugin a `MessageRateLimiter` at the requested rate, clamped to 1000 a second, default 200. Four Unit tests cover the default and clamp; the full sandbox suite passes (119 passed, 14 skipped). Not done: the other `limits` fields (`memoryMb`, `cpuPercent`, ...) are still not read from the manifest.

## Sandbox: manifest process limits reach the launchers

`PluginLimits` now also carries `MemoryMb`, `MaxProcesses`, `CpuSeconds` and `WallSeconds`; `ToJobLimits()` clamps them to host ceilings (1024 MB, 64 processes, 3600 s) and defaults memory to 256 MB. `ISandboxLauncher.Start` takes an optional `JobLimits`, the Windows and Linux launchers use it (macOS ignores it), and `PluginHost` passes the manifest's limits on launch. Unit tests cover the clamp and the defaults; the sandbox suite passes (120 passed, 14 skipped). Not verified: that each launcher enforces `WallSeconds` (not tested), and the Linux container run was not repeated.

## Sandbox: idle heartbeat sweep and restart

`PluginHost.Sweep(TimeSpan)` and `PluginPool<T>.Sweep(Func<T,bool>)` probe idle shared instances with a heartbeat and end and remove the ones that do not answer, so the next start launches a fresh process. Leased instances are never probed. Two Unit tests (hung idle instance replaced, leased instance not probed); sandbox pool, host and heartbeat tests: 18 passed. Not tested end to end with a hung real plugin through the host. A heartbeat of a leased instance inside the call loop is still open.

## Sandbox: request context from a validated principal

`RequestContext.FromPrincipal` builds the context from the principal the host's token validator produced, bounded by the token's `exp`, refusing anonymous, subject-less or expired principals. Two Unit tests with `FakeTimeProvider`; the RequestContext tests: 12 passed. RFC 8693 token exchange is not part of it (the STS converts the credential before the host sees the principal).

## Sandbox: folder access revoke for the AppContainer

`AppContainerLauncher.Revoke(directory)` removes the container's access rules that `Grant` added and reports whether any existed. Integration test on Windows (grant, revoke, second revoke returns false, no rule left): passed. The launcher does not call it automatically, and the AppContainer profile itself is not deleted.

## Sandbox: Survive named-pipe transport

`SurviveConnection` plus a `survive` mode in the test plugin: a plugin keeps running after its caller disconnects, a second caller reconnects with a new session key and gets `lifecycle.reconnected` (session 2) from the same process, and the plugin exits when the window passes with no caller. Two Integration tests passed on Windows. Not done: launcher wiring (job without kill-on-close, AppContainer pipe ACL, watchdog).

## Sandbox: events no longer count as unanswered frames; message-rate path through the host tested

Found by a flood test: `FrameChannel` kept the MAC of every frame without an ack, including one-way events, so a plugin crashed after 64 events ("too many unanswered frames") because nothing can answer an event. Only requests and heartbeats are tracked now (Unit test with 200 events, then 65 requests refused). A host-level test (`Call_PluginFloodsFrames_IsStoppedAfterSustainedWindowsOverTheRate`) shows a plugin that stays over its message rate is stopped. 103 Sandbox tests passed on Windows.

## Erasure entry point

`IErasureEntryPoint` (Abstractions) with the default `ErasureEntryPoint` (registered by `AddEventSourcing`): records an erasure request under a new id. Two Unit tests passed. The guarded ASP.NET controller is not built because no host in the repository uses event sourcing yet.

## Survive in an AppContainer (Windows)

One Integration test starts the plugin in an AppContainer, detaches, and a host reconnects and echoes; the four Survive tests passed on Windows. Not done: the `ISandboxLauncher` option, the watchdog and the Linux side.
