## Sandbox: message rate limiter

`MessageRateLimiter` counts frames per one-second window, drops the excess and counts it, and reports a sustained excess (default three windows in a row). `BrokeredPlugin.RateLimiter` applies it in the call loop: excess frames are skipped, a sustained excess throws `InvalidOperationException`. Three Unit tests with `FakeTimeProvider` pass. Not done: reading the limit from a manifest `msgPerSec` field, and heartbeat enforcement.

## Sandbox: heartbeat check

`PluginHeartbeat.Check(plugin, timeout)` sends a heartbeat frame and waits for the frame that acknowledges it; on a miss it disposes the plugin and returns false. `PlainPlugin.Dispose` is now safe to call twice. Two Unit tests pass (echo answers; a sleeping plugin is declared hung and stopped). Not done: running the check on a schedule and the restart policy.

## Sandbox: manifest process limits reach the launchers

`PluginLimits` now also carries `MemoryMb`, `MaxProcesses`, `CpuSeconds` and `WallSeconds`; `ToJobLimits()` clamps them to host ceilings (1024 MB, 64 processes, 3600 s) and defaults memory to 256 MB. `ISandboxLauncher.Start` takes an optional `JobLimits`, the Windows and Linux launchers use it (macOS ignores it), and `PluginHost` passes the manifest's limits on launch. Unit tests cover the clamp and the defaults; the sandbox suite passes (120 passed, 14 skipped). Not verified: that each launcher enforces `WallSeconds` (not tested), and the Linux container run was not repeated.

## Sandbox: events no longer count as unanswered frames; message-rate path through the host tested

Found by a flood test: `FrameChannel` kept the MAC of every frame without an ack, including one-way events, so a plugin crashed after 64 events ("too many unanswered frames") because nothing can answer an event. Only requests and heartbeats are tracked now (Unit test with 200 events, then 65 requests refused). A host-level test (`Call_PluginFloodsFrames_IsStoppedAfterSustainedWindowsOverTheRate`) shows a plugin that stays over its message rate is stopped. 103 Sandbox tests passed on Windows.

## Error handling with correlation: ProblemDetailsExceptionHandler

`OoBDev.AspNetCore.Mvc` gained `ProblemDetailsExceptionHandler` (an `IExceptionHandler`), `TryAddProblemDetailsExceptionHandler(configuration)` and `UseProblemDetailsExceptionHandler()`. An unhandled exception returns an RFC 9457 500 with `traceId`, `correlationId`, `requestId` and `instance`, logs the exception once with the same identifiers, and never returns the exception message. `OoBDev:ProblemDetails:IncludeErrorLocation` (default false) adds `errorLocation` (exception type, method, file, line) for development and test. Two Unit tests in `OoBDev.AspNetCore.Tests` pass; the example API is not wired to it yet. Docs: project readme and observability practices.
