# Owner decisions (always apply)

- **UI:** MVVM with command binding. Commands are real, retestable `ICommand` types with injected dependencies, not lambdas. For JS/TS pick frameworks with view-model binding and note where they diverge from MVVM.
- **Authentication:** OAuth 2.0 / OIDC / JWT bearer. Applications validate tokens and never store passwords. Services understand only JWT; the STS or an edge adapter converts any other credential (API key, HMAC, basic, Kerberos/NTLM, SAML). RFC 8693 token exchange is optional and config-gated. See `docs/patterns-discovery/03-practices-and-conventions/09-authentication-practices.md`.
- **HTTP and authorization:** REST first, OpenAPI is the contract, errors are RFC 9457 problem details. OData over HTTP `QUERY` (with `POST` fallback) and GraphQL are under evaluation beside the custom search syntax, with no breaking change to it. RBAC with application rights (`[ApplicationRight]`); roles are translated to rights in middleware; same checks on every API surface (docs 10 and 11 in that folder).
- **Dependencies:** see the `coding-standards` rule. Owner answers are recorded under each verdict in `docs/patterns-discovery/05-industry-alternatives/`.
- **Scope:** all BinaryDataDecoders features are migrated (phases are priority order, not selection). Check `C:\repo\mine\binary-data-decoders` before migrating; the old `Incoming/BinaryDecoders` copy is gone.
- **Best coverage:** when migrating or building a feature, compare every source (incoming code and all harvest projects), not the first one found; use the best-covered, tested implementation as the base and merge missing parts. Rejections are allowed but are documented with the reason (`docs/migration/README.md`).
- **Migrate everything, including the surroundings (owner, 2026-10-30):** when migrating a project, review all of it, not just code: the project guide, `.claude` (rules, skills, hooks, settings), docs, open questions, TODO and BACKLOG, UIs, tests, scripts and future plans. Each item is migrated or rejected with a recorded reason, so no plan or workflow is lost.
- **Reference projects:** before building a feature from scratch, check `docs/harvest-candidates.md` for an existing implementation in the owner's other repositories (read-only references; event-sourcing material may be copied sanitized, with the source recorded in the readme (owner, 2026-11-11)).
- **Process:** read `/TODO.md` (the `Backlog:` sections) before starting work, and update it when work finishes.
- **Open questions:** track questions for the owner in `OPEN-QUESTIONS.md` (`open-questions` rule); a chat answer counts as an answer.
- **Migration documentation pattern (owner, 2026-10-30):** import a migrated project's docs whole under `docs/applications/{app-name}/` (reusable designs to `docs/design/<Feature>/`, protocols to `docs/protocols/`), keep its change history and bug reports, and track the move in a transient map in `docs/migration/`. Do not clean up or delete imported history until every migration is done; then a documentation cleanup plan integrates it. Living documents, not ADRs.
- **Memory lives in the repository (owner, 2026-10-30):** save every memory (owner preferences, feedback, references) as a file in `.claude/memory/` with a one-line entry in `.claude/memory/MEMORY.md`, committed with the work; never in a user-specific folder. Existing user-folder memories were copied there.
- **Database schema is a final state (owner, 2026-11-24):** manage schemas as the desired end state applied through `OoBDev.Data.DesiredState`, not as migration chains; no new `dotnet ef migrations add`. Retirement of the existing EF migration projects follows [the plan](../../docs/design/DesiredStateDatabase/final-state-plan.md) once confirmed (Q37).
